# Ultimate Solver Optimization Plan

## Research Summary

Three research agents analyzed the codebase, Timefold documentation, and academic literature. Key findings:

**CRITICAL BUG:** `AdaptiveSolverListener` is NEVER registered with the Timefold solver. It's only in `HybridCpSatSolverService`, but when CP-SAT fails, Timefold runs without it. The `SOFT_WEIGHT_MULTIPLIER` is permanently stuck at 0.3. ALL adaptive behavior is dead.

**Academic insights:**
- ITC-2002 winner used Kempe chain swaps + tabu search
- ITC-2007 winner used graph coloring + adaptive large neighborhood search
- ITC-2011 winner used Great Deluge acceptance (1 parameter, no tuning)
- Step Counting Hill Climbing was specifically designed for timetabling
- Sequential variable assignment can make CH 30x faster

## 7 Changes (Ranked by Impact)

### 1. Fix AdaptiveSolverListener Registration (CRITICAL BUG FIX)
The listener is never registered. `SOFT_WEIGHT_MULTIPLIER` stuck at 0.3 permanently. Soft weights are at 30% of intended value. Move factories are in permanent "high violations" mode.

**Fix:** Register `AdaptiveSolverListener` in `SolverService.java` via `SolverManager.solveAndListen()` callback, or in `OptaPlannerConfig.solverFactory()` via `SolverConfig.setSolverEventListenerList()`.

### 2. Switch to Step Counting Hill Climbing (ITC-2011 technique)
Replace the complex triple acceptor (Tabu + Late Acceptance + Simulated Annealing) with **Step Counting Hill Climbing** — specifically designed for university timetabling by Bykov & Petrovic (2013).

**Why:** The current triple acceptor has 3 parameters to tune and allows too much wandering in infeasible regions. SCHC has one parameter (`stepCountingHillClimbingSize`) and is more robust for timetabling.

```xml
<acceptor>
    <stepCountingHillClimbingSize>400</stepCountingHillClimbingSize>
    <stepCountingHillClimbingType>SIMULATED_ANNEALING</stepCountingHillClimbingType>
</acceptor>
```

### 3. Add Strategic Oscillation Forager (hard/soft balance)
When no hard improvement is available, prioritize softer improvements instead of accepting hard-worsening moves.

```xml
<forager>
    <acceptedCountLimit>8</acceptedCountLimit>
    <finalistPodiumType>STRATEGIC_OSCILLATION</finalistPodiumType>
</forager>
```

### 4. Sequential Variable Assignment in CH (30x faster CH)
Currently CH evaluates 41×122=5,002 candidates per lesson. Sequential assignment does timeslot first (41), then room (122) = 163 candidates. **30x fewer evaluations.**

```xml
<constructionHeuristic>
    <constructionHeuristicType>FIRST_FIT_DECREASING</constructionHeuristicType>
    <changeMoveSelector>
        <valueSelector variableName="timeslot"/>
    </changeMoveSelector>
    <changeMoveSelector>
        <valueSelector variableName="room"/>
    </changeMoveSelector>
</constructionHeuristic>
```

### 5. Enable Ruin-and-Recreate (escape mechanism)
Currently disabled by default. When hard score gets stuck, this destroys a conflict cluster and rebuilds it. It's the most powerful escape mechanism for stuck hard violations.

**Fix:** Set `solver_ruin_recreate_enabled` to `true` in database or change default in `RuinAndRecreateMoveFactory`.

### 6. Use entityTabuRatio + Diminished Returns
Replace fixed `entityTabuSize=120` with ratio-based (scales automatically). Add diminished returns termination.

```xml
<entityTabuRatio>0.02</entityTabuRatio>
```

### 7. Fix AdaptiveSolverListener log format + MAX_POSSIBLE_VIOLATIONS
- `{:.2f}` is Python syntax, not Java SLF4J → change to `{}`
- `MAX_POSSIBLE_VIOLATIONS=9160` is too large → reduce to `1000`
